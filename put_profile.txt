Put optimization experiments -- 2026-10-05
=========================================

Baseline: the already optimized fingerprint-first Dict at task start.
Go 1.26.4 linux/amd64, AMD Ryzen Threadripper 3960X. Timing runs pinned to CPU 2
with -cpu=1; five repeats for primary comparisons and three for additional
key/value types. Medians are exploratory measurements, not statistical claims.
MB below means decimal megabytes. CPU profiles collected separately.

Kept changes
------------
1. Probe control bytes in freeSlot rather than int64 indexes. Reuse the empty
   slot returned by find for a new key when there are no holes. Rebuilds and
   tombstones still require a fresh freeSlot search. Hash int keys inline in Put,
   preserving custom hash precedence and default hashes. Probing-only experiment:
   million-entry grown/presized construction 96.36/63.98 -> 75.66/46.92 ms.

2. Allocate exactly hint entries in presized constructors instead of every
   spare slot allowed by the index load limit. Inserting beyond the hint still
   works through append growth and the original rebuild threshold. Keep both
   constructors small enough to inline, allowing local Dict headers to stay on
   the stack. Headers escaping their caller still need a header allocation.
   A direct NewDictSize initializer avoids its delegate exceeding the inline
   budget after the delegate itself became inlineable.

3. Coallocate indexes and control bytes in one pointer-free aligned int64
   allocation. Powers-of-two sizes >= 8 allow exactly size control bytes in
   size/8 extra cells. unsafe.Slice exposes only that byte tail; the index slice
   capacity excludes it. Get's byte accesses and int64 index range are retained.
   Strict checkptr tests validate the byte view. Dict field layout is unchanged.

4. Reuse metadata and entry buffers for same-size compaction when capacity
   permits. Copy live entries toward the front in insertion order, then clear
   trailing entries to remove duplicate GC roots. Different-size rebuilds still
   allocate new storage, including shrink after deletion. Tests check buffer
   identity, cleared pointer-bearing tails, model agreement, order and metadata.

Primary results (median, five repeats)
-------------------------------------
Million entries, grown: 96.359 -> 76.420 ms (21% faster), 57 -> 38 allocations;
127,278,560 -> 127,283,168 B allocated. Growing bytes are essentially unchanged,
with allocator rounding slightly increasing them. This is a speed/count win,
not a substantial byte reduction for unhinted construction.
Million entries, presized: 63.985 -> 45.320 ms (29% faster), 4 -> 2 allocations;
63,619,168 -> 50,880,512 B (20% less).
1,000 entries, grown: 29.644 -> 25.251 us, 27 -> 18 allocations.
1,000 entries, presized: 16.087 -> 11.976 us; 67,680 -> 51,200 B; 4 -> 2 allocs.
1,000-entry overwrite: 10.15 -> 7.659 ns. Million-entry overwrite: 55.49 -> 52.46 ns.

Additional cases: at 65,536 keys, presized strings 3.320 -> 2.515 ms; custom
hash 1.554 -> 1.291 ms; 128-byte values 4.080 -> 3.350 ms. Growing large-value
construction was essentially flat (7.065/7.067 ms), with fewer allocations.

Steady churn (initial growth warmed outside timing; one delete + Put per cycle):
1,024 live keys: 35.10 -> 29.18 ns. 65,536 live keys: 56.79 -> 39.84 ns (30%
faster), about 73 -> 0 B/cycle. Final runs report zero mallocs/cycle; baseline
has fractional mallocs that the standard allocs/op metric rounds down to zero.
Earlier unwarmed runs include amortized initial growth bytes; reuse eliminates
recurring compaction allocations, not all future growth allocations.

Read performance guardrails
--------------------------
Integer hits at 1,024/16,384/1,048,576: 6.608/12.07/105.3 -> 6.620/12.15/103.8 ns.
Large integer misses: 20.33 -> 20.34 ns. Million-key string hits/misses:
360.9/36.16 -> 360.5/36.10 ns. No meaningful Get regression in these runs.
Isolated 1,000-key scans: 708.3 -> 709.0 ns; large scans showed no regression.
All and Get implementations and entry layout were unchanged. Allocation
placement can influence timing; do not attribute scan gains directly to Put.

Profiles
--------
Baseline freeSlot accounts for 60.60% flat CPU samples, find 10.95%, zeroing
11.44%, rebuild 55.42% cumulative. Final freeSlot is 18.27% flat; zeroing is
20.62% flat, rebuildEntries 61.68% cumulative. Nested cumulative percentages
must not be added to flat ones. Allocation-space profiles attribute essentially
all grown-build bytes to rebuilds. Profile total GB increases because faster
code completes more builds; compare B/op rather than total profile GB.

Validation
----------
go test ./..., go vet ./..., and go test -gcflags=all=-d=checkptr=2 ./... passed.
Default/colliding fuzz runs passed with 10,518 / 30,340 executions. One timed
constant-hash run ended with context deadline exceeded at shutdown without
reporting a failing input. Its cached corpus and 20,000 further executions
passed on a single-worker, execution-count rerun; string fuzzing also passed
20,000 executions. All mutation/property/invariant tests pass.

Reproduction
------------
go test -c -o /tmp/insdict-put.test
taskset -c 2 /tmp/insdict-put.test -test.run '^$' -test.bench '^BenchmarkDict(Put|PutPresized|PutOverwrite)$/^n=(10|1000|1000000)$' -test.benchtime=400ms -test.count=5 -test.cpu=1
taskset -c 2 /tmp/insdict-put.test -test.run '^$' -test.bench '^BenchmarkPut(Strings|LargeValues|CustomHash|Churn)$' -test.benchtime=500ms -test.count=5 -test.cpu=1
# Use individual BenchmarkPointGetInt/String leaves and BenchmarkDictScanValues
# for read guardrails. Profile an individual construction leaf separately:
taskset -c 2 /tmp/insdict-put.test -test.run '^$' -test.bench '^BenchmarkDictPut$/^n=1000000$' -test.benchtime=5s -test.cpu=1 -test.cpuprofile=/tmp/insdict-put.cpu -test.memprofile=/tmp/insdict-put.mem
go tool pprof -top /tmp/insdict-put.test /tmp/insdict-put.cpu
go tool pprof -top -alloc_space /tmp/insdict-put.test /tmp/insdict-put.mem
