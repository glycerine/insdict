Implemented optimization -- follow-up results, 2026-10-05
=========================================================

Production changes in insdict.go:
- Get2 fuses hashing, probing, and the value return; Get delegates to Get2.
- Common int keys use inline Mix64, preserving default hashes and custom hash
  precedence. Other supported key types still use defaultHash.
- One control byte per index slot: 0=empty, 1=deleted, 128..255=occupied with
  the high seven hash bits in the low seven control bits.
- Lookup checks control bytes FIRST. Most mismatched fingerprints and absent
  lookups never access the int64 indexes or entry array. Matching fingerprints
  still require full hash and key equality. Tombstones continue the probe.
- Put, Del, and rebuild maintain both metadata and indexes. Write probing uses
  the same filtering; passing the precomputed tag keeps find inlineable (cost
  74 under the compiler's budget of 80).
- Dense entries, their field layout, hash values, probe sequence, and insertion
  order remain unchanged. The tags slice follows the existing Dict fields.

Historical investigation BEFORE production optimization
======================================================
The following section describes the earlier baseline and benchmark-only
candidates; its statement that production is unchanged applies to that stage.

Get performance investigation -- 2026-10-05
============================================

Environment: Go 1.26.4, linux/amd64, AMD Ryzen Threadripper 3960X.
Repeated comparisons below use one Go execution thread (-cpu=1), pinned to
CPU 2 with taskset. These are exploratory medians, not statistical claims.
CPU profiles were collected separately, without CPU pinning or concurrent
benchmarks. Source attribution remains valid; absolute profile-run timings
are not directly comparable to the pinned measurements.

Changes: get_bench_test.go adds point-Get benchmarks and three test-only
candidates. insdict.go and the existing README benchmarks are unchanged.
Validation: go test ./... passed, including comparisons of the candidates
with production Get for empty dictionaries, present/absent keys, zero values,
tombstones, strings, custom hashes, and a constant collision hash.

Benchmark design
----------------
Each operation performs one value-only point lookup. Integer and 20-byte
string keys are tested at 1,024, 16,384, and 1,048,576 stored entries. Queries
are a deterministic shuffled permutation covering n distinct keys per cycle,
not a small hot query ring. Hits visit all stored keys. Misses use disjoint
keys. Mixed queries alternate hits and misses (50% each). String queries use
distinct storage from stored keys, so hits require actual string equality.
All query generation, hashing for probe statistics, construction, and tag
construction happen outside timing. The loop uses a mask instead of division;
the accumulated lookup results escape through a package-level sink.

Grown tables have 50% index occupancy at these sizes. Sparse tables are
rebuilt with twice the slots (25% occupancy). Reported table_B includes
allocated index and entry backing arrays, plus sidecar tags for Tagged.
It excludes key payload allocations, queries, dictionary header, and Go map
memory. In this implementation sparse rebuilding also doubles entry capacity;
it is a memory/latency experiment, not a recommended production setting.
All measured lookup leaves reported zero allocations.

Candidates
----------
Fused: generic value-only lookup, with hash selection in the lookup routine
and a direct return from the matched entry. Removes the hashOf call and
repeated entry indexing/bounds checking. Retains defaultHash and the original
probe sequence, hash/key verification, custom hashing, and int64 indices.

TypedInt: concrete int/int version of Fused, with inline Mix64 hashing.
Removes the generic defaultHash call/type switch and changes code generation.
It is an upper-bound experiment for specialization, not a drop-in generic
API change. The benefits cannot all be attributed to type-switch instructions
alone; generated code can change scheduling and memory-latency overlap.

Tagged: generic Fused lookup plus one byte per index slot containing the high
8 hash bits. The existing index handles empty/deleted status; a tag mismatch
rejects a collision before reading entries[ix]. Full hash/key verification
still follows a tag match. This preserves full int64 indexes and the original
probe sequence. Tags are constructed from the populated table for this read-only
experiment; production adoption would require maintenance in Put/Del/rebuild.

Key results (median ns per lookup, pinned)
-----------------------------------------
Integer hits               Dict    Map     Fused   TypedInt   Tagged
1,024                      11.30    8.81     8.58      5.72      8.69
16,384                     18.59   10.84    16.71     13.45     14.47
1,048,576                 157.30   69.81   155.00    118.50    120.00

The generic fused path improves small hits about 24%, medium hits about 10%,
and large hits only about 1.5%. TypedInt improves hits about 49%, 28%, and 25%.
Tagged improves medium/large hits about 22%/24%; its small-table result is
essentially the Fused gain, rather than an additional fingerprint benefit.
For million-entry integer misses, Dict=108.40, Map=65.32, Tagged=61.12;
Tagged improves about 44%. Million-entry mixed: Dict=138.60, Tagged=106.00.

At 50% occupancy, the million-entry integer table allocates 58.67 MiB;
fingerprints add 2 MiB (about 3.4%). Average probes are 1.388 for integer hits
and about 2 for misses. Ordinary hits inspect an entry at every occupied
probe; tags should reduce this toward one entry read per hit, and nearly zero
for misses, assuming well-distributed fingerprint bits. This is an explanation
of the expected mechanism, not a measured hardware cache-miss count.

pprof findings
--------------
Small integer hits (1,024): hashOf including defaultHash accounts for 38.31%
of total CPU samples; defaultHash including Mix64 is 30.61%; find is 44.99%.
These cumulative percentages overlap and must not be added. Compiler output
shows Get and find inline, while Get2, hashOf, and defaultHash do not inline.
The defaultHash type switch remains in compiled integer lookup code.

Large integer hits: find has 94.68% of total samples. About 3.63 seconds are
at the empty-slot check, and 6.74 seconds at the entry hash/key check, out of
11.08 seconds sampled. pprof -disasm shows the hot instructions are comparisons
immediately following the index and entry-hash loads; the integer key comparison
itself gets almost no samples. This strongly suggests dependent memory latency,
not expensive integer equality. CPU sampling alone does not prove cache misses;
hardware counters would be needed to quantify them. About 4% of this profile
is construction/probe instrumentation, since CPU profiling includes untimed setup.

String hits (16,384): find has 64.60% flat / 86.69% cumulative; memeqbody 21.94%;
xxhash.Sum64 4.46%. A wholesale replacement of xxhash would not address the main
cost of this workload. Longer strings could change that conclusion.

Recommendations, in order
-------------------------
1. Prototype the generic fused lookup in production, especially removing the
   hashOf boundary and repeated entry indexing. It already matches/slightly
   beats Go map for small integer hits without changing table layout. Preserve
   Get2's presence flag and validate both APIs: the measured candidates return
   only values, and their exact speedups need not transfer to a Get2 rewrite.

2. For large-table Gets, add fingerprints to the index structure. The scalar
   sidecar already gives useful hit/miss gains and preserves int64 capacity.
   Then investigate grouped control bytes (8 slots at a time) to reduce branch
   and scattered probing costs further. The installed Go runtime's map.go and
   runtime_fast64.go show this approach: hash fingerprints reject most candidates
   before key access. Keep dense insertion-ordered entries for All(). Grouped
   probing can coexist with that entry array, but its write-path cost and
   iteration/cache impact need measurement; the scalar candidate proves only
   the simpler read-only filtering approach.

3. Consider an integer hashing fast path or optional concrete specialization.
   TypedInt shows substantial headroom. Merely caching a func(K) uint64 in each
   Dict removes type dispatch but introduces an indirect call, so benchmark it
   before choosing it. Preserve custom-hash behavior and the documented panic
   for unsupported/named default-hash key types. Avoid runtime-internal map
   hashing/linkname tricks: they complicate stability and deterministic layout.

4. Investigate adaptive 32-bit indexes for small tables with an automatic 64-bit
   fallback. This can recover the earlier index footprint without limiting the
   API to 2^31 entries. Branch once before the probe loop; reserve encodings for
   empty/tombstone slots and promote safely. This idea was not implemented or
   measured here. Narrow indexes alone cannot remove the index-to-entry dependency.

5. Lower occupancy alone is less attractive. The pinned sparse million-entry
   Dict improves hits 157.5 -> 144.9 and misses 108.4 -> 88.78 ns, while doubling
   allocated table capacity. Tagged becomes slower when sparse (hits 120.3 ->
   132.4; misses 61.12 -> 81.09), illustrating the footprint tradeoff. Prefer
   filtering first rather than globally increasing table sizes.

Follow-up measurements: combine fusion/fast hashing with tags; include near-2/3
occupancy, deletion churn/tombstones, other key/value sizes, and another machine.
Check Put/Del and All performance before adopting an index-layout change.
The experiments here use insertion-only tables with int values; they do not
establish universal speedups or production write-path costs.
